# Falsification of the "capability is a row" claim

A criticism written against the actual build. Every line below points at real code, a real endpoint, or a measured row count. The claim under attack is quoted verbatim from the live article `https://miscsubjects.com/a/the-unified-loop` (title: "891 capabilities, 14,071 tokens: capability as a row, not a definition") and from STATE.md line 2782.

## The conditions under which this claim is false

1. **The 14,071 figure is false the moment the model ingests `?registry=1`.** The protocol's own read-more links (`functions/_lib/object_contract.js:504,541,667`) point every reader at `GET /api/dispatch?registry=1`. That endpoint (`functions/api/dispatch.js:2510-2512`) calls `registryFromRows(dir, …)` (`functions/_lib/object_contract.js:2479`), which returns **every enabled row** as a `directoryRowToObject` payload. Measured live on 2026-07-26: `?registry=1` returns 1,608,289 bytes ≈ **402,072 tokens** (877 objects, `curl -s https://miscsubjects.com/api/dispatch?registry=1 | wc -c`). That is **2.7× the 149,187** the architecture is sold as beating. The claim "adding a row does not change the second number" is true only for the narrow workload where the model never pulls the registry into context. Any planner, cold-boot, or "show me everything" workload that ingests the registry re-couples catalogue size to input cost — and couples it *worse* than the MCP-definitions baseline it replaces, because a row carries its full contract (`description`, `input_schema`, `auth`, examples) where a tool definition can be trimmed.

2. **The claim is false once row count exceeds what `loadDirectory` can snapshot cheaply.** `functions/api/dispatch.js:413-426` loads the *entire* directory on *every* dispatch and caches it in KV for 30 s (`directory:snapshot`, `expirationTtl: 60`). The 14,071 measurement is a model-input figure; it says nothing about the per-request edge cost of hydrating 892 rows (content ~493 KB, schema ~101 KB — `D1_QUERY` aggregation on 2026-07-26). At 892 rows this is invisible to the model budget; at 89,200 rows the `SELECT … FROM directory` + JSON-stringify-everything-in-KV path is what breaks, and the claim's "infrastructure primitive" framing hides that the catalog cost moved from the model bill to the edge bill with no stated ceiling. The claim provides no number at which `loadDirectory` stops being free; that number is the falsification condition.

3. **The claim is false the first time a row's `content`/`input_schema` grows large enough to dominate a single `?key=` fetch.** Step 4 of the loop reads one contract via `?key=<key>&format=markdown`. A single row's contract is returned in full (`directoryRowToObject`). The 14,071 number assumes each on-demand read is small. There is no per-row size cap enforced in code (`functions/api/dispatch.js:413` selects `content` and `input_schema` with no `LENGTH()` guard). One 200 KB agent row (the `agent` type already averages 4,284 chars/row × 57 = 244,186 chars, `D1_QUERY` aggregation) read into context re-couples size to cost on the on-demand path too.

## Where the complexity actually went

The claim says complexity is eliminated, not relocated. It is relocated — into 892 hand-maintained rows. Counting the real cost:

- **Adding a row is not free; it is a write that invalidates the 30 s KV snapshot.** `functions/api/dispatch.js:423` puts `directory:snapshot` with `expirationTtl: 60`. A new row does not enter the cache until the TTL expires or the cache is explicitly busted. The build relies on staleness ageing out; there is no write-through invalidation in `loadDirectory`. So "adding a row does not change the [14,071] number" is true while *failing to change the running snapshot* for up to 60 seconds — the row exists in D1 and is invisible to dispatch until the cache dies. That is a correctness cost the claim does not account for.

- **Every row carries its own credential wiring (`auth` column), target string, content template, and schema.** The `fn` type alone (`runFn`, `functions/api/dispatch.js:1167-1180`) requires: a `target` matching an entry in `FN_MAP` (a 60-symbol hand-maintained map assembled at `functions/api/dispatch.js:3492`), a `content` body that `JSON.parse`'s to an array, and a docstring convention parsed by `stripDocs`/`extractDocs` (`functions/api/dispatch.js:437-455`). A malformed `content` JSON returns `ERR:fn:bad_content_json` at runtime, not at add-time. There is no schema validation on insert — `ADD_ROW`/`EDIT_ROW` take free text. So the cost of a row is not "one INSERT"; it is "one INSERT plus the runtime risk that the row's template doesn't parse until something invokes it." 480 `fn` rows × this risk = 480 unverified parse contracts.

- **The `contract_hash` mechanism proves the relocation, not the elimination.** `functions/api/dispatch.js:2128-2131` recomputes `objectContractFingerprint(row)` at invoke time and 409s a scoped token if the row changed. This exists *because* rows are mutable and the system must defend against them drifting under a live token. A static tool definition has no such problem — it is pinned at prompt-build time. The contract-hash check is pure overhead introduced by choosing rows-over-definitions; it is complexity that would not exist in the baseline.

- **891 → 892.** The article and STATE.md (line 2782) both say 891. `D1_QUERY | SELECT COUNT(*) FROM directory` returned **892** on 2026-07-26; enabled = 879, disabled = 13; `?registry=1` serves 877 (2 filtered by `TEST_ID_PATTERN`, `functions/_lib/object_contract.js:2486`). The headline number in the published claim is already stale by ≥1. A claim whose central evidence is a row count cannot keep that count right by hand at 892 rows, which is itself the maintenance objection: the catalogue drifts faster than the prose about it.

## What the measurement does not show

The 149,187 vs 14,071 comparison (`STATE.md:2733,2782`) holds one workload constant and silently varies the unit being measured.

- **149,187 = 891 tool definitions in the prompt. 14,071 = 9 built-in tools in the prompt + capabilities reached over HTTP on demand.** These are not the same object counted two ways. STATE.md line 2782 states it plainly: the 14,071 run had "9 built-in tools" and reached capabilities "over HTTP." The comparison subtracts 882 tool definitions and adds an HTTP transport; it does not show "891 rows cost less than 891 definitions." It shows "9 tools + a network cost less than 891 tools." That is a different claim, and the network cost (latency, the `loadDirectory` snapshot, the `?ask=` server-side scan) is moved off the model's token bill entirely — which is the point, but it is not what the sentence "the same 891 as rows costs 14,071" says.

- **The comparison assumes the model uses tools sparsely.** 149,187 is paid every turn regardless of use; 14,071 is paid every turn *plus* one `?ask=` + one `?key=` fetch per tool actually used. At a workload that invokes, say, 40 distinct capabilities per turn, the on-demand path adds ~40 contract reads to the context. None of those reads are in the 14,071 measurement, which (per STATE.md) ran "a session … reaching all 891 capabilities over HTTP" — a session whose token total was measured at the *gateway*, i.e. before the on-demand reads re-enter the model's context as tool outputs. The breakeven — how many on-demand reads before 14,071 + read-tokens exceeds a trimmed-definitions baseline — is not in the claim because no trimmed-definitions baseline was measured. The only baseline measured is the full 891-definition MCP attach, which is the worst case for definitions, not a representative one.

- **149,187 and 14,071 come from different models on different runs.** STATE.md line 2733: the 149,187 figure is a Kimi run; a GLM run on the same attach measured 149,443. The 14,071 figure (line 2782) is a separate session. Tokenizers differ across models; "input tokens" is not a model-independent unit. The comparison presents two numbers as if they are the same currency and they are not — the 6,256-token gap between the two "149k" runs alone (~4%) is larger than the entire 14,109-vs-14,071 "tie" the article cites as evidence of structural equivalence (line 2780).

- **"Adding a row does not change the second number" was not tested by adding a row.** No measurement in STATE.md adds a row and re-runs the 14,071 figure. The statement is an inference from the architecture, not a measurement. The architecture supports the inference *only* because the directory is not in the prompt; but the registry endpoint (`?registry=1`, 402k tokens) and the `?ask=` scan (which iterates all rows server-side, `answerAsk(Object.values(dir), …)`, `functions/api/dispatch.js:2519`) mean adding a row *does* change two observable numbers — registry payload size and ask-scan compute — neither of which the claim names.

## What is unproven

1. **The receipt is not signed.** `receiptPayload` (`functions/_lib/object_contract.js:2217`) and `publicReceiptPayload` (`:2034`) return SHA-256 digests of input, output, and contract (`fingerprints`, computed at `:1910-1912` via `sha256Hex`). These are integrity hashes computed and stored by the same edge that ran the invocation. There is no HMAC, no `crypto.subtle.sign`, no `importKey` anywhere in `object_contract.js`, `invocation_log.js`, or `event_log.js` (grep returns zero hits). The protocol advertises a `verify(receipt)` verb (`object_contract.js:2429`) but "verify" means "re-fetch and compare hashes," not cryptographic verification — and the hashes verify against the *live* row (`objectContractFingerprint(row || {key})` recomputes from the row at verify time, `:1912`), so a row edit after the fact would make a stale receipt mismatch and look like the invocation never happened, with no way to prove the row was edited. The claim calls this a "receipt" in the audit sense; it is an append-only log row, not a signed receipt. Single-authority, unsigned, mutable-source.

2. **Step 8 ("external review … is recorded") is not enforced by any endpoint.** The eight-step loop in the article is prose. Steps 1-7 map to code (`onRequestPost`/`onRequestGet` in `functions/api/dispatch.js`, `logEvent` in `functions/_lib/event_log.js`). Step 8 — "Another model reads that address, reviews it, and the review is recorded" — maps to *nothing*. Reviews are stored as a free-form array in `articles.meta.reviews` written by whoever calls ARTICLE_PUT/ART_PATCH (`functions/api/articles/[[path]].js:238`), and `OBJECTION_LOG` is a capability the model may or may not call. There is no code that requires a review to occur, no code that verifies one occurred, and no code that closes the loop if it did not. The article itself concedes the loop is "recursive in one specific way: step 8 can trigger step 1 again" — but that recursion is optional and unenforced. A claim that "eight steps all run end to end" is false for step 8 by construction: it runs only if a model chooses to run it.

3. **The `contract_hash` pin is opt-in and absent for the owner plane.** `functions/api/dispatch.js:2128-2131` checks `cap.contract_hash` — but only inside the `if (tokenInfo)` block. The owner (terminal-key) plane (`full = isBuildAuthed`, e.g. `:1886`) bypasses every gate in `affAuth` (`:1886` returns `can_invoke_this: true` unconditionally). So the contract-hash guarantee — that a scoped token cannot invoke a row that changed since it was minted — does not apply to the operator who owns 100% of the traffic today. STATE.md line 2782's 14,071 measurement was an owner-key session. The strongest property the claim can make (contract drift is detected) holds for tokens, not for the session that produced the evidence.

4. **The idempotency/dedup guard is a KV race, not a guarantee.** `functions/api/dispatch.js:1948-2049` documents the dedupe as collapsing identical rapid-fire calls, with an explicit fallback (line 2044) for "the winner's receipt id was not readable in time (D1 replica lag)" — in which case the duplicate is *not* re-fired and the caller is told to look in the ledger. So "a receipt for every action" has a known hole: under D1 replica lag, a duplicate is suppressed and the original receipt id is unknown to the caller. The claim says receipts are "fetchable at their own address"; under lag, the address exists but the caller was not given it.

5. **"One installation" is one operator.** The claim's own article says "The figures come from one installation." That installation is a single-custodian control plane (object_contract.js `:1150`: "private single-custodian control plane by design"). There is no second operator's data. The 14,071 number is n=1 and the n is the same person who wrote the claim.

## What would make the claim stronger

- **Re-run 14,071 after adding a row, and publish the new number.** The claim's load-bearing sentence ("adding a row does not change the second number") is an inference; one INSERT + one gateway log read would make it a measurement. Cost: minutes.
- **Add a `?registry=1&format=summary` that returns keys only, not full contracts, and cite its token cost.** This closes the 402k-token hole in objection 1 and makes the registry safe for a model to ingest. Cost: one new filter in `registryFromRows`.
- **Sign the receipt with an HMAC over (id, ts, input_hash, output_hash, contract_hash) using a build secret, and verify the signature in `receiptPayload`.** Turns "append-only log row" into "signed receipt" and makes post-hoc row edits detectable. Cost: one `importKey` + one `sign` in `object_contract.js`.
- **Measure a trimmed-definitions baseline (e.g. 20 most-used tools as definitions, rest on-demand) against the 14,071 row figure.** The claim only beats the *full* 891-definition attach. A trimmed-definitions comparator is the workload a real operator runs; without it the claim wins against a strawman. Cost: one gateway session.
- **Enforce step 8 or drop it from the loop.** Either wire a required-review gate into the publish step, or reduce the loop to seven steps. Calling a social process a loop step that "runs end to end" is the weakest link in the claim and the cheapest to fix by honest renaming. Cost: a paragraph.
- **Pin the row count to the live count in the article, or state it as a snapshot date.** "891" is already 892. A claim whose evidence is a count should not let the count drift in the headline. Cost: one number.
